Porokh OTA Distribution

Public OTA (Over-the-Air) distribution repository for Porokh, the student examination and practice application.

This repository hosts signed update metadata and encrypted application bundles distributed through GitHub Releases.

It is intentionally separate from the main application source code.

Repository Purpose

The Porokh OTA architecture uses two repositories:

Repository| Responsibility
"porokh" (https://github.com/towkirahmedrony/porokh)| Application source, OTA implementation, Android app and publishing automation
"porokh-ota" (https://github.com/towkirahmedrony/porokh-ota)| Public OTA channel metadata, public verification key and encrypted release assets

This repository must never contain application source code, private keys, credentials, environment files or unencrypted application bundles.

Update Channels

Porokh currently supports two Android OTA channels.

Channel| Purpose
"staging-android"| Testing updates before production release
"production-android"| Stable updates for production users

Each channel has its own pointer document.

Channel Pointer URLs

Production:

https://raw.githubusercontent.com/towkirahmedrony/porokh-ota/main/channels/production-android.json

Staging:

https://raw.githubusercontent.com/towkirahmedrony/porokh-ota/main/channels/staging-android.json

The application fetches the pointer for its configured channel. It validates the document and its signature before trusting the update metadata.

A channel pointer identifies the latest published release for that channel.

Release Structure

Each OTA release is published as an immutable GitHub Release.

Release tag format:

ota-<channel>-r<revision>

Example:

ota-staging-android-r123

Each release contains four assets:

Asset| Purpose
Encrypted bundle (".zip.enc")| Application update payload
"manifest.json"| Release metadata and embedded pointer signature
"manifest.json.sig"| Detached signature for the manifest
"SHA256SUMS"| SHA-256 checksums for release assets

Release asset filenames and metadata are generated by the publisher. Do not rename or manually replace published assets.

Published release tags and assets must be treated as immutable. A new update must use a new revision and release tag.

Update Discovery and Verification

The update process follows this sequence:

1. The application fetches its channel pointer from this repository.
2. The application validates the pointer structure, channel and compatibility metadata.
3. The Ed25519 signature is verified using the public key trusted by the application.
4. The application checks version and revision rules to prevent downgrade or replay.
5. The encrypted bundle is downloaded from the specified GitHub Release.
6. The native Capacitor updater verifies the bundle using the RSA key-v2 trust mechanism and its integrity checks.
7. The update is staged and activated according to the application's safety gates.
8. The application confirms successful startup through "notifyAppReady()".

Important Security Distinction

Porokh uses two separate cryptographic mechanisms:

Ed25519

- Protects OTA pointer metadata.
- Helps the application detect unauthorized changes to release metadata.
- Its private key must remain in GitHub Actions Secrets.

RSA key-v2

- Protects the encrypted application bundle.
- Its public key is embedded in the Android application.
- Native bundle verification remains the bundle's trust anchor.

The Ed25519 pointer signature does not replace native RSA bundle verification.

Publishing Workflow

OTA publishing automation lives in the main "porokh" repository:

porokh/.github/workflows/ota-release.yml

The publisher is implemented in:

porokh/scripts/publish-ota-release.ts

The publishing workflow is responsible for:

- Preparing and validating the release plan.
- Packaging the application bundle.
- Encrypting and signing the bundle.
- Generating release metadata and checksums.
- Creating the GitHub Release.
- Uploading the release assets.
- Updating the appropriate channel pointer.
- Reading the pointer back and verifying the published release.

The OTA repository itself does not build the application or execute the publishing pipeline.

First-Time Setup

The first successful staging publish initializes:

channels/staging-android.json
keys/ed25519-public.pem

The production pointer is created when the first production release is published.

Do not create or modify generated pointer files manually unless following an explicitly reviewed recovery procedure.

Rollback and Recovery

Rollback is managed through the publishing automation in the main "porokh" repository.

A rollback changes the channel pointer to refer to a previously published release while preserving monotonic generation/revision rules.

Important considerations:

- Existing release assets are not overwritten.
- Rollback must preserve valid signatures and compatibility metadata.
- An older release may be rejected by devices already running a newer version because of downgrade protection.
- A full-fleet rollback may require republishing the last-known-good bundle with a higher revision.
- If a release is created but asset uploading fails, the incomplete release may need manual cleanup before retrying.
- Never manually modify a production pointer without verifying its signature and compatibility metadata.

See the publishing and rollback implementation in the main repository before performing recovery operations.

Security Rules

The following rules are mandatory:

1. Never upload private keys or GitHub tokens to this repository.
2. Never upload unencrypted application bundles.
3. Never commit ".env" files, credentials or signing keystores.
4. Never replace an existing release asset with different content.
5. Never publish staging content to the production channel.
6. Never publish an unsigned or invalidly signed channel pointer.
7. Do not lower native or schema compatibility requirements without an explicit compatibility review.
8. Do not bypass version, revision or downgrade validation.
9. Keep the Ed25519 private key and RSA private key exclusively in protected GitHub Actions Secrets.
10. Review all publishing and rollback changes before production use.

The public Ed25519 verification key is not secret. It may be distributed with the application and stored in this repository.

Operational Notes

- OTA updates modify the web application bundle, not the native Android binary.
- Changes requiring native Android code, plugins or native configuration still require a new APK.
- Existing APKs must already include the GitHub-based OTA discovery implementation to use this distribution system.
- Devices with unsupported WebView cryptography may reject OTA updates safely.
- A failed OTA verification must never cause the application to install an untrusted bundle.
- Production auto-publishing must remain disabled until staging has been successfully verified on a physical device.
